Gemini Multi-Prompt TTS Player Deployment Guide

This document matches the current production architecture:
- Frontend and backend run in one Cloud Run service
- Firestore stores schedules, runs, and global rate-limit counters
- Firestore also stores manual async runs for refresh-safe manual generation
- Cloud Storage stores scheduled WAV and JSON artifacts
- Cloud Scheduler triggers due-schedule polling

========================================================================
1. Pre-Deploy Inspection
========================================================================

Every production deploy must start with a read-only inspection pass.
Do not deploy first and inspect later.

Required inspection commands, in this exact order:

1. Confirm active project and account
   - `gcloud config list --format=json`
   - `gcloud auth list --format=json`
2. Inspect existing Cloud Run services
   - `gcloud run services list --project gen-lang-client-0354055629 --format=json`
3. Inspect existing Cloud Scheduler jobs
   - `gcloud scheduler jobs list --location us-central1 --project gen-lang-client-0354055629 --format=json`
4. Inspect existing secrets
   - `gcloud secrets list --project gen-lang-client-0354055629 --format=json`
5. Inspect existing service accounts
   - `gcloud iam service-accounts list --project gen-lang-client-0354055629 --format=json`
6. Inspect existing buckets
   - `gcloud storage buckets list --project gen-lang-client-0354055629 --format=json`
7. Inspect Firestore database
   - `gcloud firestore databases describe --database='(default)' --project gen-lang-client-0354055629 --format=json`
8. Inspect Firestore composite indexes
   - `gcloud firestore indexes composite list --project gen-lang-client-0354055629 --format=json`

Deployment must not continue until this inspection pass is complete.

2. Minimal-Change Deployment Rules
========================================================================

Default rule: reuse existing GCP resources whenever they already satisfy the
app's needs.

Resource reuse policy:

- If the target Cloud Run service already exists, deploy to that service name.
- If a suitable service account already exists and already has the required
  permissions, reuse it.
- If a secret already exists, reuse the same secret name or existing reference
  rather than inventing a new name.
- If a bucket already exists and is already intended for this app, reuse it.
- If the scheduler job already exists, update it instead of creating a second
  job.
- If Firestore is present but a query fails because of missing indexes, create
  only the required index. Do not rename collections or redesign storage.
- If Cloud Storage signed URLs are used, verify the runtime service account can
  sign blobs before deploying.

Avoid these unless truly necessary:

- Renaming Cloud Run services
- Rotating secret names only for cosmetic consistency
- Replacing a working service account with a different one
- Creating a second scheduler job for the same polling endpoint
- Creating duplicate artifact buckets

========================================================================
3. Deployment Decision Table
========================================================================

Use these rules after the inspection pass:

- Existing Cloud Run service found:
  - Deploy to the existing service.
- No Cloud Run service found:
  - Create the service with the documented service name.
- Existing scheduler job found:
  - Update the existing job in place.
- No scheduler job found:
  - Create the job once.
- Existing secret found:
  - Keep using the same secret name or same mounted env var source.
- No secret found:
  - Create it only if the app cannot run without it.
- Existing artifact bucket found:
  - Reuse it.
- No artifact bucket found:
  - Create a dedicated bucket for this app.
- Firestore query fails due to missing index:
  - Create the index only.

5. Required Secrets
========================================================================

Supported secret/env sources:

- `GEMINI_API_KEY`
- `GEMINI_API_KEYS`
- `APP_ADMIN_PASSWORD`
- `SCHEDULER_SHARED_SECRET`
- `ADMIN_SESSION_SECRET`

`ADMIN_SESSION_SECRET` is strongly recommended. The app can fall back to
`APP_ADMIN_PASSWORD`, but that is only for compatibility and should not be the
long-term production setup.

Current project note:

- The existing Secret Manager secret `gemini-key` is already available and can
  be mapped into runtime env var `GEMINI_API_KEY`.
- If you want primary/backup Gemini failover, provide `GEMINI_API_KEYS` as a
  comma-separated env var or inject an equivalent value from Secret Manager.
- Current production setup maps both `GEMINI_API_KEY` and `GEMINI_API_KEYS` to
  `gemini-key:latest`.
- The other three values can be provided either via Secret Manager or direct
  Cloud Run env vars if you are minimizing project changes.
- If you rely on GCS signed URLs, the runtime service account also needs
  `roles/iam.serviceAccountTokenCreator` on itself.

8. Cloud Run Deploy Command
========================================================================

Deploy only after the inspection pass above.

If the service already exists, this command updates it in place.

gcloud run deploy gemini-multi-prompt-tts-player ^
  --source . ^
  --project gen-lang-client-0354055629 ^
  --region us-central1 ^
  --allow-unauthenticated ^
  --service-account 305416593596-compute@developer.gserviceaccount.com ^
  --set-secrets GEMINI_API_KEY=GEMINI_API_KEY:latest ^
  --set-secrets GEMINI_API_KEYS=GEMINI_API_KEY:latest ^
  --set-secrets APP_ADMIN_PASSWORD=APP_ADMIN_PASSWORD:latest ^
  --set-secrets ADMIN_SESSION_SECRET=ADMIN_SESSION_SECRET:latest ^
  --set-secrets SCHEDULER_SHARED_SECRET=SCHEDULER_SHARED_SECRET:latest ^
  --env-vars-file C:\path\to\cloudrun-env.yaml ^
  --min-instances 1 ^
  --max-instances 10 ^
  --concurrency 80 ^
  --timeout 300 ^
  --port 8080 ^
  --memory 1Gi

Notes:

- Do not set `PORT` in `--set-env-vars`
- `min-instances=1` reduces cold starts
- `memory=1Gi` is the current production value; it was raised after long manual
  runs exceeded the earlier `512Mi` limit during audio merge/upload
- `max-instances=10` is the current scale setting used to handle concurrent scheduled work
- Do not include `PORT` in `--set-env-vars`; Cloud Run reserves it
- On Windows PowerShell, do not use a long raw `--set-env-vars "A=...,B=...,C=..."`
  string as the primary deploy method for production. On 2026-03-14 this caused
  a real incident where multiple env vars were concatenated into
  `APP_ADMIN_PASSWORD`, which broke login.
- For production deploys, prefer `--env-vars-file` for non-secret env vars and
  use separate `--set-secrets` flags for secrets. Reserve `--set-env-vars` /
  `--update-env-vars` for small targeted changes only.
- Before treating deployment as complete, verify the runtime service account has
  blob-signing permission if signed URLs are expected

9. Scheduler Job
========================================================================

Current internal polling endpoint:

- `POST /api/internal/run-due-schedules`

Required header:

- `X-Internal-Key: YOUR_SCHEDULER_SHARED_SECRET`

If the job already exists, update it instead of creating a duplicate.

Example create command:

gcloud scheduler jobs create http schedule-runner ^
  --project=gen-lang-client-0354055629 ^
  --location=us-central1 ^
  --schedule="*/5 * * * *" ^
  --time-zone="Europe/Paris" ^
  --uri="https://gemini-multi-prompt-tts-player-305416593596.us-central1.run.app/api/internal/run-due-schedules" ^
  --http-method=POST ^
  --headers="X-Internal-Key=YOUR_SCHEDULER_SHARED_SECRET,Content-Type=application/json" ^
  --message-body="{}"

Example update command:

gcloud scheduler jobs update http schedule-runner ^
  --project=gen-lang-client-0354055629 ^
  --location=us-central1 ^
  --schedule="*/5 * * * *" ^
  --time-zone="Europe/Paris" ^
  --uri="https://gemini-multi-prompt-tts-player-305416593596.us-central1.run.app/api/internal/run-due-schedules" ^
  --update-headers="X-Internal-Key=YOUR_SCHEDULER_SHARED_SECRET,Content-Type=application/json" ^
  --message-body="{}"

10. Security Notes
========================================================================

Current production hardening in the app:

- Admin auth uses signed `HttpOnly` cookies
- Browser write endpoints enforce same-origin CSRF checks via `Origin`/`Referer`
- Manual generation now runs server-side, so browser refresh does not interrupt in-progress manual runs
- `/api/artifacts/...` requires admin auth
- Artifact path traversal is blocked in the storage layer
- Daily global rate limits are stored in Firestore:
  - login: 100/day
  - text: 200/day
  - tts: 200/day

Limitations:

- If Firestore is unavailable, the rate limiter falls back to local memory
- That fallback is only for degraded operation, not the normal production path

========================================================================
11. Player Behavior
========================================================================

Current player behavior for scheduled runs:

- Scheduled audio is prefetched from top to bottom
- Prefetch is serial: one item at a time
- Each item shows a clear state:
  - `Queued`
  - `Downloading audio...`
  - `Decoding audio...`
  - `Cached locally`
  - `Failed`
- Cached scheduled audio and text are persisted locally in IndexedDB until manually cleared

Mandatory env verification after deploy:

- Inspect `spec.template.spec.containers[0].env` in `gcloud run services describe ... --format=json`
- Confirm `APP_ADMIN_PASSWORD` is a standalone value, not a concatenated string
- Confirm `ADMIN_SESSION_SECRET`, `SCHEDULER_SHARED_SECRET`, `GCS_BUCKET_NAME`,
  `APP_DEFAULT_TIMEZONE`, Firestore collection names, and `TTS_CHUNK_CONCURRENCY`
  each appear as separate env entries
- If login suddenly fails after deploy, check this before debugging auth logic

Signed URL permission verification:

- `gcloud iam service-accounts get-iam-policy 305416593596-compute@developer.gserviceaccount.com --project gen-lang-client-0354055629`
- Confirm the policy includes:
  - member `serviceAccount:305416593596-compute@developer.gserviceaccount.com`
  - role `roles/iam.serviceAccountTokenCreator`

Required fix if missing:

`gcloud iam service-accounts add-iam-policy-binding 305416593596-compute@developer.gserviceaccount.com --project gen-lang-client-0354055629 --member="serviceAccount:305416593596-compute@developer.gserviceaccount.com" --role="roles/iam.serviceAccountTokenCreator"`

Known manual-run artifact failure mode:

- If logs show `Permission 'iam.serviceAccounts.signBlob' denied on resource`
  after `audio.merge.success`, the WAV may already exist in GCS even though the
  manual run is marked failed.
- Current code now mitigates this in two ways:
  - `saveAudio()` falls back to `/api/artifacts/...` if signed URL generation fails
  - `manualRunRunner` writes `audioPath` / `audioDownloadUrl` back to Firestore
    immediately after audio save so the GUI can still fetch the file

Known deployment failure mode from 2026-03-14:

- Symptom: browser login returns `Invalid password` immediately after a deploy
- Root cause: a PowerShell deploy used an unsafe long `--set-env-vars` string,
  and Cloud Run stored one long concatenated value under `APP_ADMIN_PASSWORD`
- Fix:
  - re-run the env update using `--env-vars-file` or a safe targeted
    `gcloud run services update ... --update-env-vars "KEY=value,KEY2=value2"`
  - re-check `gcloud run services describe ... --format=json`
  - verify `APP_ADMIN_PASSWORD` exactly matches the intended password
